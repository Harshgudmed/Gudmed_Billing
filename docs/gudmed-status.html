Section 01Found today — a screen that was down

This was not found by reading code. It was found by driving the real browser through the module and watching the network tab.

Appointments “Today” tab and search returned HTTP 500 fixed

What the front desk saw: the Today tab and any search for a patient name simply failed. Not a slow list — a hard error.

GET /api/appointments?…status=scheduled,confirmed,checked_in,in_progress  → 500
GET /api/appointments?…search=ram                                        → 500

Inconsistent query result: Field patient is required to return data, got `null`
  at getAll (appointmentController.js:97)

The cause was not in the code. The database held 165 foreign keys. 41 pointed at User. Zero pointed at Patient. schema.prisma declares patient Patient @relation(…, onDelete: Cascade), so the schema believed deleting a patient removed their appointments. Without the constraint that line was a comment.

The 17 Patient constraints had been dropped during a bulk data trim — deleting 850,000 patients was taking 15+ minutes because 17 tables re-checked their key per deleted row — on what was believed to be a throwaway copy. That copy became the working database. On 26 June 2026 the trim ran, nothing cascaded, and 381 appointments were left pointing at patients that no longer existed. Prisma treats a required relation as guaranteed, so one orphan anywhere in a page of results took down the whole endpoint.

Fixed: 381 orphaned appointments and their 381 queue rows removed; all 18 foreign keys restored (17 by migration, plus ClinicalOrder whose relation was never declared in the schema at all, so Prisma had never asked for it).

inserting an orphan row  → REFUSED (violates foreign key constraint)
deleting a patient       → their appointments 1 → 0   (cascade works)
Today tab                → 200, 475 rows
search "ram"             → 200, 11 rows
trigram search indexes   → all 5 still present (deliberately excluded from the migration)

The database still does not enforce which hospital a patient belongs to open

The restored keys guarantee a referenced patient exists. They do not guarantee it belongs to the same hospital — patientId references Patient(id), and every hospital's patients share that table, so a cross-tenant id satisfies the constraint and stores cleanly.

Today there are zero cross-tenant rows: isOwned() in the controllers is holding. But that is code, and code has gaps — one hospital could read another's radiology orders until this month. Enforcing it in Postgres needs a UNIQUE index on Patient(organizationId, id) and composite keys on all 18 children. Worth doing; it is a decision, not something to slip in.

node backend/scripts/check-orphans.mjs now reports any cross-tenant row the day it appears.

A radiology scan could be moved onto another patient by a PATCH fixed

The update handlers validate with .passthrough() schemas, so any key the caller sends is kept and spread into prisma.update({ data }). Each handler kept its own hand-written list of fields to delete first, and the lists had drifted — Laboratory deleted six, Radiology deleted two.

POST  radiology order for patient A     → RAD-2026-27-000002
PATCH { patientId: B, orderNumber: "RAD-HACKED-0001" }
      → the scan moved to patient B, under a number the caller chose

One patient's scan filed under another patient is the worst outcome a radiology system has. Six hand-written lists replaced by one shared table (lib/stripIdentity.js); the same exploit re-run afterwards left patientId, orderNumber and examId untouched while status — the field that legitimately changes — updated correctly.

6 regression tests, one of which drives the real controller — a correct list nobody calls protects nothing, which is exactly how Radiology was left exposed

Money columns are Float — real risk, no damage yet partly

68 of the 92 Float columns hold money (the other 24 are genuine measurements — temperature, SpO₂, weight — and are correctly Float). Binary floating point cannot represent 0.10, so a long column of them drifts.

Measured honestly: nothing has drifted. 63 invoices, 12 payments, all exact to two decimals; every total equals subtotal − discount + tax. The protection is round2() — which appears in 10 backend files while 39 touch money. So it is a habit, not a guarantee.

Two places where the habit had lapsed are fixed: the patient portal summed 25 invoices unrounded (a patient could see ₹12,345.67000000001 as their own balance), and the Razorpay paise→rupee conversion shown beside the Pay button.

A standing tripwire now reads all 60 money columns from information_schema — new columns are covered automatically — and fails naming the table and column the first time a value below one paisa is stored.

Not done: the Float → Decimal migration itself. 68 columns, 54 files, 38 arithmetic sites; in Prisma a Decimal is an object, not a number, so every +, * and comparison changes behaviour. Recommended as its own day, with Billing, Pharmacy and IPD — not bundled into a deploy.

Section 04The audit tool — why the old reports were wrong

The harness drove each module from a hand-written list of button and tab names. That list is always shorter than the module, and it goes stale silently.

Appointments was “audited” having touched about a sixth of it

Its entry was two fields — a search placeholder and four tab names. The module actually has five tabs, nine icon-only buttons, five filters, five dialogs, two tables, three different pagination mechanisms and 99 controls. The tool even counted icon-only buttons and then never clicked them, because its only icon clicker required a title attribute those buttons do not have.

Three further defects would have corrupted this report exactly as they corrupted the Patients one: no date-filter handling at all; a false “fires per keystroke” verdict caused by waiting 1,200 ms between characters and thereby defeating every debounce; and wrong profile sub-tab labels.

Rebuilt around discovery and a coverage ledger done

A module is now three fields — a key, a URL, a name. Everything else is read from the live DOM on every run, so the same command works on all 14+ modules without being told anything about them, and a button added next month is covered without editing anything.

Naming was the hard part. A bare <Button><ChevronLeft/></Button> has no text, no aria-label and no title — Appointments has six. lucide stamps its class on the svg, so lucide-chevron-left is a real name hiding in the markup. That is what makes them clickable and reportable when missed.

Every run now ends with found N · clicked M · skipped-write · skipped-destructive · unreachable · NOT CLICKED — and lists the unclicked ones by name. A run that claims everything passed without naming what it left out is the failure this replaces.

node e2e/audit.mjs --deep --module <key> --lighthouse --json e2e/audit-report/<key>.json

It found five bugs in itself, which is the strongest evidence it works: unnamed buttons named after the discovery counter (so one button consumed a whole category's budget while 31 calendar-day buttons beside it were never touched); unreachable controls retried forever; the final sweep overwriting deliberate skips with “NOT CLICKED”; a recursive profiler walk that made the app itself the bottleneck; and a Lighthouse login that scored the login page.

e2e/discover.mjs · netwatch.mjs · profiler.mjs · lighthouse.mjs · fixtures/appointmentLifecycle.mjs

The check that was missing: did the response answer the question?

Everything above measures how big a response was and how long it took. None of it asks whether the response is the answer to the request. A call can be fast, small, 200 OK — and wrong:

?status=pending   → rows come back that are not pending
?limit=15         → sixteen rows arrive
?doctorId=X       → another doctor's rows are in the list
?date=2026-08-01  → rows from other days
meta.total = 500  → but the first page is empty

None of that surfaces as an error. The screen renders, the numbers look plausible, and a filter that quietly does not filter is how one doctor ends up reading another's list. Size and timing are blind to all of it.

e2e/contract.mjs now compares every request's query string against the rows that came back, on every call the harness records. It is deliberately conservative — it judges a parameter only where it maps unambiguously to a field on the returned rows, because a check that guesses produces noise, and noisy findings are how real ones get ignored.

This check is new, which means the four modules audited before it existed were never subjected to it. All five are being re-run rather than assumed clean — an audit that skipped a check is not an audit that passed it.

What it checks that a code review cannot

  • The same URL fetched twice in one action — two components, one need
  • Two different URLs returning byte-identical bodies — a cache being bypassed
  • A query refetched with nothing changed since the last action — a bad useEffect dependency array
  • Responses over 100 KB, calls over 200 ms, any 4xx/5xx, limit= with three or more digits
  • A cursor-pointer element with no React onClick — looks clickable, does nothing
  • Which components re-rendered, by name — not just how many commits
  • Per API call: status · method · path · KB · ms · row count · query string · payload

A line that names a catalogue row also carries priceSource: ‘unpriced’ when the catalogue had no price — so “which bills went out at zero?” is answerable from the invoice JSON alone. That is a question someone thought to make answerable in advance.

Two ways a line escapes the catalogue open

serviceId that does not exist  →  201 · ₹0   [unpriced]
sourceType=lab + bad sourceId  →  404       refused
no id at all, unitPrice ₹5000  →  201 · ₹5000  client’s price

The first is a known, documented trade-off — the code says so: “serviceId is exempt: it is not proven to always be a BillingService id, and rejecting it would break billing for lines that work today.” The consequence is that a wrong or foreign serviceId produces a free line instead of an error. It is at least marked.

The second is deliberate — an ad-hoc charge has no catalogue to consult, so it keeps the price it arrived with. Necessary, and also the one hole through which any amount can reach an invoice.

A correction to an earlier draft of this section: it stated that a plain service line was priced by the client. That was wrong. serviceId becomes the catalogue key itself — item.sourceType || (item.serviceId ? ‘service’ : null) — so those lines are repriced. Caught by running it before writing it up, which is the only reason it is not a fourth false finding in this document.
