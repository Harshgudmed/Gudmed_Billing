What is genuinely fine

  • CLS 0 everywhere — nothing jumps as the page loads. That is real and worth keeping.
  • No response over 100 KB in Queue or Pharmacy — Queue's largest is 9.7 KB.
  • Pharmacy's tab switching is free — five of six tabs fire zero requests.
  • Queue uses limit=10 — no rule-5 violation.
  • No 4xx or 5xx anywhere, now that the Appointments 500 is fixed.

Those four are real, but they are not the picture. The picture is that all three modules are slow, on the most favourable machine they will ever run on.

Requests that should never have been made

These are not slow calls — they are calls with no reason to exist. Each one was caught by comparing a request against the same request in an earlier action: same URL, same bytes back, nothing about its inputs changed in between. That is the signature of a useEffect whose dependency array is wrong.

The worst of these is Queue's Billing tab: one press of Next costs four requests and only one of them was asked for. On a hospital connection that is four round trips where one would do.

What the profiler shows — and it is not fine

The hook records which components actually rendered, by name, not just how many commits happened. Three things stand out, and none of them is acceptable:

  • The sidebar repaints on every keystroke. Typing three characters into a search box re-rendered Navigation and all its NavLink children 99 times. The sidebar has nothing to do with a search box.
  • Closed dialogs re-render. AppointmentFormDialog rendered 10 times and AppointmentPatientDialog once while neither was open. Work done for something nobody can see.
  • One filter change costs 808 renders. In Queue, changing a single dropdown re-rendered Primitive.div 808 times; Pharmacy spent 2,254 ms inside one action.

The cause is one line long: nothing in src/ is wrapped in React.memo, and no callback is wrapped in useCallback, so every state change at the top re-renders everything below it. This is why the same symptom appears identically in all three modules — it is not three bugs, it is one.

Two honest caveats on these numbers. The profiler itself was slowing the page down until it was made cheaper mid-audit — the earlier figures in this document were inflated by the observer, and the ones quoted here were taken after that fix. And render counts vary between runs; what does not vary is which components appear, which is the part that matters.

How the top three are actually done

#1 — Stop the shell repainting on every keystroke

The sidebar re-renders because Shell receives a new navItems array and new callbacks on every parent render, and nothing below it is memoised. Three changes, one file:

// src/App.jsx

// 1. The shell only depends on its props. Memo makes React skip it when they
//    have not changed — which is every keystroke in every module.
const Shell = memo(function Shell({ navItems, navbarColor, hospitalName, homeTo, footer, children }) {
  …unchanged…
})

// 2. The nav list must be the SAME array between renders, or memo compares a new
//    reference every time and skips nothing.
const navItems = useMemo(() => [...], [role, modulesEnabled])

// 3. Anything passed down as a prop gets the same treatment.
const handleX = useCallback(…, [deps])

Measured target: NavLink 208× → 0 on a filter change, 99× → 0 while typing. Verify with the profiler in the audit, not by eye.

#2 — Make ?resource=stats stop shipping 2 MB and a password hash

The same edit fixes both. Today it loads every column of every doctor plus every commission and adds them up in JavaScript:

// backend/src/controllers/doctorAccountabilityController.js  (~line 117)

// BEFORE — 28 columns per doctor including passwordHash, plus every commission row
const doctors = await db.user.findMany({
  where: { organizationId, role: 'doctor' },
  include: { commissionConfig: true, commissions: true },
})
const stats = doctors.map(d => ({ pendingAmount: d.commissions.filter(…).reduce(…) , … }))

// AFTER — the database does the arithmetic, and only named columns come back
const [doctors, totals] = await Promise.all([
  db.user.findMany({
    where: { organizationId, role: 'doctor' },
    select: { id: true, fullName: true, commissionConfig: { select: { commissionRate: true, commissionType: true, isActive: true } } },
  }),
  db.doctorCommission.groupBy({
    by: ['doctorId', 'status'],
    where: { organizationId },
    _sum: { commissionAmount: true, invoiceAmount: true },
    _count: true,
  }),
])
// then join the two in memory — a few hundred rows, not every commission ever written

Measured target: 2,065 KB → under 100 KB, and passwordHash / invitationToken gone. The identical change was already made to ?resource=doctors earlier today, which is how this one was found.

#3 — Make /pharmacy/stats stop taking 1.2 seconds for 400 bytes

A tiny response with a long time is an index problem, never a payload problem. The route aggregates across 196,744 drugs. Two steps, in this order:

-- 1. find out what it is actually doing before changing anything
EXPLAIN ANALYZE <the query the stats route runs>;
--    a Seq Scan on PharmacyDrug is the expected answer

-- 2. index the columns it filters and groups on, e.g.
CREATE INDEX CONCURRENTLY "PharmacyDrug_org_stock_idx"
  ON "PharmacyDrug" ("organizationId", "quantityInStock");
CREATE INDEX CONCURRENTLY "PharmacyBatch_org_expiry_idx"
  ON "PharmacyBatch" ("organizationId", "expiryDate") WHERE status = 'active';

CONCURRENTLY matters — it builds without locking the table, and this one has 196,744 rows. Confirm with EXPLAIN ANALYZE afterwards that the scan is gone; a created index that the planner ignores has changed nothing.

Measured target: 1,204 ms → tens of milliseconds, on every page load of the module.

If only three get done

  1. #1 — memoise the app shell. It is the root cause in every module measured, and it is one file.
  2. #7 — the stats select. It removes 2 MB and closes a credential leak in the same edit.
  3. #2 — index /pharmacy/stats. 1.2 seconds off every page load of that module.

None of the twenty has been done. They are measured, not fixed — and that gap is the honest summary of the work so far: 60-plus findings, six repairs.

Two rules for this whole list. Do one step at a time and re-measure before starting the next, or you will not know which change did what. And re-run the whole deep audit after each one — several of these fixes touch shared code, and the fastest way to learn that memoising the shell broke a module is for the harness to say so.

The eighth row is not optional. Every performance score in this document was taken against the Vite dev server, which does not minify and is far slower than what a hospital loads. Those numbers are useful for comparing modules against each other and useless as an absolute. The TBT, the render counts, the payload sizes and the query timings are all real; the Lighthouse performance score is not.
