9 August — what the day actually found

Two production bugs, one accident caused by the audit itself, four defects in the audit tool, and a duplication scan of the whole repository. Written as it happened, including the parts that go against the tool.

The 43% coverage figure published earlier today is WITHDRAWN — see finding 3

Finding 1Two modules 400 on every search — one commit, five days live

Pre-Triage and Death Certificates cannot be searched at all critical

GET /api/pre-triage?search=r            400   8ms
GET /api/death-certificates?search=ra   400   3ms
→ 19 critical events in the Pre-Triage walk, 13 in Death Certificates,
  every one of them this request

Both come from commit d09c061 fix(search): standardize multi-word patient search across all modules of 5 August, which replaced eleven hand-written search blocks with one shared helper. Consolidating them was right — CLAUDE.md rule 9 asks for exactly that. Two of the eleven were never checked against their own schema.

Death Certificates searches a column called causeOfDeath. There is no such column: the statutory form stores the cause as a chain of four — immediateCause (a), antecedentCauseB, C, D.

Pre-Triage passes relation = null, which tells the helper the five patient columns live on the model itself. PreTriage is a walk-in record — someone who is not a patient yet — and carries only firstName, lastName and phone. Three of the five injected columns do not exist.

The blast radius is bigger than the search box. Both the count() and the findMany() fail, so the list and the stat cards go together. And because the bad clause is only built when a search term is present, each filter works alone and dies the moment it is combined with a search — the exact case CLAUDE.md rule 10 warns about: "one filter at a time is the easy case and it is not the case that breaks."

Finding 2The audit switched fifteen modules off — and then measured the Dashboard fifteen times

The tool did this, not the app withdrawn results

icon: unlabelled div0>div0>button1
  PATCH /settings → {"modulesEnabled":{"patients":false, …}}
icon: unlabelled div0>div1>button1
  PATCH /settings → {"patients":false,"consultations":false, …}
… thirteen more

Settings → Modules renders each module's on/off switch as a button with no text, no aria-label, no title and no icon class. Discovery could only name it by its position in the DOM. The audit's two safety filters both match on the name, so both were blind to it, and the walk pressed all fifteen.

Why that is worse than a broken switch. A disabled module's route is filtered out of the router, so /admin/laboratory fell through to the catch-all and rendered the Dashboard, with the URL quietly changing to /admin. Twelve of sixteen routes did that. The audit kept going and measured the Dashboard under twelve different module names — page sizes, Lighthouse scores, coverage, all of it, filed against modules it had never opened.

before repair:  4/16 routes land where they should — 12 do NOT
after repair:  16/16 routes land where they should

Two real findings fell out of the accident. First, those toggles are invisible to a screen reader for the same reason they were invisible to the audit. Second, opening a disabled module silently shows the Dashboard with no message — the user is told nothing, and will report the module as missing.

What stops it recurring — two independent guards, because one regex is not a guard:

  • the walk never presses a control with no accessible name; it reports it instead
  • node e2e/restore-modules.mjs runs after every module and repairs any toggle that was turned off. Its first version guessed the password, got a 401 and printed "skipping" — a guard that silently does nothing. Credentials now come from helpers.js.

Finding 3The 43% coverage figure is withdrawn

It was measured while the toggles were being switched off underneath it retracted

The all-seventeen-module figure published this morning — 539 of 1,245 controls, 43% — cannot be trusted. Settings was walked partway through the sequence, so every module audited after it may have been the Dashboard wearing another module's name.

Some of it survives. Laboratory found 246 controls and called /api/laboratory; Pre-Triage got 400s from /api/pre-triage. The Dashboard calls neither, so those runs really did open their module. But the point of a coverage number is that you do not have to check it call by call, and this one you do. So it goes.

It stays here struck through rather than deleted. Two of Appointments' twenty-four findings were withdrawn the same way earlier; hiding them would make the surviving ones less trustworthy, not more.

Finding 5Two more counting errors, both of which made the app look worse than it is

The same ten rows counted twice, and nine phone numbers counted as misses fixed

A clickable table row was discovered both as a card and as a row. The row walk clicked all ten; the card walk then looked for cards the first walk had consumed and reported ten "unreachable" — one set of ten patients, counted twice, half of it as failure.

clickableCard  0/10  clicked · 10 unreachable
tableRow      10/10  clicked          ← the same ten elements

And nine of Patients' fourteen uncovered controls were tel: links to patients' own phone numbers. Clicking one hands the browser to the OS dialler and leaves the app, so it can never be part of a module's coverage — counting it as missed is a lie about the walk, not a gap in it.

The percentage now has a reachable denominator. With destructive buttons, write buttons and external links in the denominator, 100% was arithmetically impossible however complete the walk. Every run now prints both:

found 50 · clicked 27 · skipped-write 2 · skipped-destructive 1
         · skipped-external 9 · unreachable 0 · NOT CLICKED 0
reachable 38 · clicked 38 · 100% of what the walk was allowed to press

Finding 6IPD bed race — safe; its own cleanup was not

Two admissions into one bed, same instant SAFE

call A → 201  admitted
call B → 409  IPD_BED_UNAVAILABLE
patients now admitted to this bed : 1

Compare-and-set holds. Worth stating because the equivalent check in Queue did fail earlier and had to be rewritten — two races were predicted, one was real.

The probe's cleanup, however, deleted three of the thirteen tables that carry an admissionId — all thirteen are onDelete: Restrict, correctly, because a vitals record must not vanish with the admission above it. The admission delete was refused, then the patient delete was refused because the admission still pointed at them, and both failures were swallowed by .catch(() => {}). It printed "cleaned up" over a database it had not cleaned. Fixed to walk all thirteen in dependency order and to count what survived; the rows left by the first run were traced and removed.

Finding 7Duplication scan of the whole repository

A new standing tool: node scripts/duplication-scan.mjs. It normalises every line — comments dropped, whitespace collapsed, string literals reduced to a placeholder — so two copies that differ only in a label still match, then reports the original line numbers.

314 shipped files · windows of 10+ normalised lines
  23 duplicated across DIFFERENT files   ← shared-lib candidates (rule 9)
  24 repeated within a single file       ← extract-a-function candidates (rule 2)

Reading a diff cannot catch this: the second copy is added in a different file, in a different week, by someone who did not know the first existed. That is how the lab report HTML came to be written twice — 156 lines in LaboratoryModule.jsx and 162 in printLabReport.js. The ranked pairs and the extraction proposals are being written up separately.

Finding 8Nine mistakes made by this work, listed against itself

A report that only records the app's faults and not the auditor's is not a report, it is a defence. These are in the order they happened. Three of them corrupted results that were published before anyone noticed, and two of them are the same mistake made twice.

The pattern in them

Mistakes 1 and 2 are one judgement made twice, in opposite directions: how many was the wrong question. The right one is is this control distinct, or is it record number N — a button, an icon, a tab and a filter are each different and all get walked; a table row is the same control rendered once per patient and fifteen of them prove what four hundred do.

Mistakes 3 and 4 are also one thing twice: stopping a process tree by killing the top of it. Both times the survivor was invisible in ps -W, which does not report command lines for MSYS processes, so "nothing to stop" was printed while two audits ran.

Mistake 5 is the one worth remembering. The audit's two safety filters both matched on a control's name. A control with no name defeated both — and a control with no name is already a finding, because a screen reader cannot use it either.
