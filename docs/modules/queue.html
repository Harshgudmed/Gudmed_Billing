A month date-range takes 3.8 seconds to return ten rows QU7 · critical

/queue?startDate=2026-08-01&endDate=2026-08-31&page=1&limit=10 — 3,793 ms for 9.5 KB and ten rows. A week takes 1,280 ms. A tiny answer that takes that long is a query problem, not a payload one: the date range is being scanned rather than indexed. On Render, with real network latency and a cold connection, this is the difference between a counter working and a counter waiting.

Re-verified 10 August. Queue, month range: re-measured as a median of 163 ms (runs 78/163/3,501). The original was a single cold-pool sample. See PERF-REVERIFY.

measured — 3793 ms (month), 1280 ms (week), 905 ms (unfiltered). e2e/audit-report/live/f-queue.log

Opening a row refetches the whole list AND loses the date filter QU3 · high

Page load asks for today: /queue?startDate=2026-08-09&endDate=2026-08-09&page=1&limit=10. Clicking a row to expand it fires /queue?page=1&limit=10 — 9.6 KB, ten rows, and no date range at all. The list silently stops being today's queue and becomes every queue entry ever, without the user touching the filter. Expanding a row should not refetch the list; refetching it without the filter that produced it is the part that changes what the counter is looking at.

measured — page load carried startDate/endDate, every row click did not. e2e/audit-report/live/f-queue.log

28 actions caused App, Navigation or NavLink to re-render. The worst is 286× in a single action. The sidebar is not part of this module and has no reason to repaint when a table pages or a filter changes — this is one memoisation gap in src/App.jsx, and every module pays for it.

Retracted 10 August — measuring error. This count came from e2e/profiler.mjs, which counted every fiber whose actualDuration was above zero. React leaves that value on a fiber after its last render, so a component that bailed out of a commit still carried the cost of whenever it did render, and the walk counted it again on every commit. The tool now compares actualStartTime against the end of the previous commit and reports self time with children subtracted. FIXED — every queue row rebuilt a five-option Select on each keystroke QUEUE-ROWMEMO · fixed

Each QueueRow carries its own priority <Select>. The row was not memoised and the module's three row handlers were rebuilt on every render, so typing one character into the queue search — which the rows do not read — re-rendered all ten rows and all fifty options.

QueueRow is now memo'd and callNext, setStatus and changePriority are useCallback'd. The second half is what makes the first half work: memo compares props by reference, so a handler rebuilt each render would have defeated it silently while looking like it had been fixed.

The profiler was counting components that had not re-rendered QUEUE-TOOLFIX · correct

Recorded as a finding against the tooling, because it is the reason a number in this report was wrong and every render count in it was inflated. e2e/profiler.mjs counted any fiber with actualDuration > 0; React leaves that value in place after a render, so untouched components were counted on every commit. It now filters on actualStartTime against the previous commit and reports selfMs with children subtracted — without that second part a router wrapping a slow module is reported as the slow thing.
